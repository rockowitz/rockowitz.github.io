Frequently Asked Questions

If you are about to report a problem, start with What information should I include in a problem report?. If something is not working and you do not know why, ddcutil environment analyses your system and makes suggestions. See also Notes on Particular Configurations.

Before reporting a problem

What information should I include in a problem report?

Run

ddcutil interrogate > ddcutil-interrogate.txt 2>&1

and attach the file. interrogate runs environment, detect --verbose, capabilities and getvcp for every display, along with a survey of the relevant kernel modules, /dev/i2c devices and /sys/class/drm contents. Nearly every question that would otherwise have to be asked is answered somewhere in that output.

Also state, in the report itself:

  • what you expected to happen and what happened instead
  • the exact command you ran, and its output
  • the monitor manufacturer and model, and how it is connected -- directly, through a hub, through a dock, or daisy chained
  • whether it ever worked, and if so with which ddcutil version
  • for anything involving the desktop, the desktop environment and its version

If the problem involves a crash, a backtrace is worth far more than a description of it. On a systemd system:

coredumpctl info ddcutil
coredumpctl gdb ddcutil        # then: bt full

Installing the debuginfo package for ddcutil and libddcutil first makes the backtrace usable; without it only function names appear.

Is this a ddcutil bug or a monitor problem?

Often the latter. The largest single category of reported problems is monitor specific: the monitor's DDC/CI implementation is incomplete, or disagrees with the Monitor Control Command Set specification, or is simply wrong.

DDC/CI gives ddcutil no way to discover what a monitor really implements. The capabilities string is the monitor's own claim about itself, and is frequently inaccurate -- see the capabilities entries below. A feature can be listed and not work, work and not be listed, or accept values that no version of the MCCS spec defines.

What that means in practice:

  • ddcutil can be made to know about a monitor's quirks through a user defined feature file, which is how undocumented feature values get names. That is a data fix, not a code fix, and you can write one yourself.
  • Where the monitor ignores a value, returns the wrong one, or needs an extra command to make a change stick, ddcutil can sometimes work around it, and several such workarounds exist. But it cannot make a monitor implement something it does not.
  • Reports are still worth filing even when nothing can be done in code. They are how the behavior of particular models becomes documented.

A monitor is not detected

ddcutil does not identify a DDC/CI capable monitor.

Check the following:

  • Is DDC/CI enabled in the monitor's On Screen Display?
  • Is driver i2c-dev loaded?
  • Does the current user have permission to access the I2C bus associated with the monitor?

Command ddcutil environment will analyze your system environment and make suggestions. See enviroment Command

I'm told my monitor doesn't support DDC/CI, but the monitor's OSD says it is enabled

Check permissions before anything else. If ddcutil cannot open /dev/i2c-N, it cannot tell a monitor that does not answer from one it was never able to ask, and the message you get is the same either way.

ls -l /dev/i2c-*
id

If the devices are owned by root:root with mode crw-------, or by group i2c and you are not in that group, that is the problem. ddcutil environment diagnoses this and says what to do. See I2C Permissions for the two approaches -- adding yourself to a group, or the uaccess udev rule that grants the logged-in user access without a group.

Note that running under sudo is a valid test but not a solution: a desktop applet or libddcutil client runs as you, not as root.

Detection fails right after login or after resume from sleep, then works later

/dev/i2c devices are made accessible to the logged in user by a udev uaccess rule, which applies an ACL when the device appears and when the session becomes active. There is a window at login, and again after resume from sleep, in which the devices exist but the ACL has not been reapplied yet. An open in that window fails with EACCES, and a monitor that cannot be opened is indistinguishable from one that has been unplugged.

ddcutil retries an EACCES open for a bounded period rather than concluding immediately that the display is gone, and the display watch machinery deliberately does not emit a mass disconnect while EACCES is being seen across the board. If you are running your own program against libddcutil, do not treat the first failed detection after resume as final.

My monitor blinks or resets repeatedly during boot after installing the udev rule

Reported against the sample rules file shipped with ddcutil 2.0 through 2.1.4. The rule matched more broadly than intended, so devices were probed during boot that should not have been, and the monitor renegotiated its mode each time. Fixed in a later release of the sample rule.

If you see this, compare your installed /usr/lib/udev/rules.d/60-ddcutil-i2c.rules (or /etc/udev/rules.d/, or the older 45-ddcutil-i2c.rules) with the version in the ddcutil source tree under data/usr/lib/udev/rules.d/, and note that a distribution package may be shipping its own variant. Removing the rule stops the symptom immediately, at the cost of needing group membership for access.

ddcutil doesn't work on my laptop.

Laptop displays do not support DDC/CI.

But recent laptops use Embedded Display Port (eDP) panels which have an I2C interface. Why doesn't ddcutil work?

The I2C connection on eDP panels implements slave address x50, which allows programs to read the EDID in the expected way. However, it does not implement slave address x37, i.e. it does not support DDC/CI.

If eDP panels did implement DDC/CI, ddcutil would support it. For each I2C bus that could possibly be associated with a monitor, as part of display detection ddcutil attempts to read the EDID at slave address x50. If successful, it then attempts to communicate on slave address x37. If that fails, and display detection is occurring in the context of ddcutil detect --verbose, ddcutil then looks for a possible reason, and checks to see if the display is a laptop. If so, it then reports that laptops to not support DDC/CI.

ddcutil can't communicate with a monitor when it's plugged into a docking station.

ddcutil does work when the monitor is plugged directly into the laptop. The problem affects DisplayPort, DVI, and HDMI connectors on the dock.

This is a problem with newer docking stations that implement DisplayPort Multi Stream Transport. Until kernel release 5.11, the drm driver layer did not implement I2C writes.

For the gory details, see this thread on the Intel-gfx developers list.

The second monitor in a DisplayPort daisy chain is not detected

Monitors chained through DisplayPort MST are reached over the first monitor's link. Whether each one gets a usable DDC channel depends on the driver and on the monitors: in some topologies every sink gets its own I2C bus, in others the whole chain shares one bus and only the first monitor answers.

Check whether a bus exists for the second monitor at all:

ddcutil detect --verbose
ls -l /sys/class/drm/card*-DP-*/ddc 2>/dev/null

If the second monitor has a DRM connector with a valid EDID but no ddc symlink and no /dev/i2c device of its own, there is nothing for ddcutil to talk to -- the same situation described for Nvidia and MST hubs, and not something ddcutil can work around. Connecting the second monitor directly to the video card is the test that settles it.

My monitor connects by USB. Will ddcutil work?

Some monitors implement MCCS over a USB HID interface instead of I2C, and ddcutil supports those -- see USB Connected Monitors. They appear in detect output with a /dev/usb/hiddev* device rather than a /dev/i2c bus. They are rare.

Two things to check if a USB connected monitor is not found:

  • whether your build has USB support at all -- ddcutil --version --verbose reports it
  • permissions on /dev/usb/hiddev*, which are separate from the /dev/i2c permissions -- see USB Permissions

For diagnostics, the USB checks are not part of interrogate; run ddcutil usbenvironment --verbose separately.

Note the distinction from a monitor connected by USB-C carrying DisplayPort, which is an ordinary DisplayPort monitor as far as ddcutil is concerned and uses I2C, not HID. A monitor's USB hub being connected changes nothing either way.

It works when connected directly but not through a USB-C or Thunderbolt dock

See USB-C DisplayPort Alt Mode for what the connector actually carries. Docks that carry DisplayPort over USB-C put an MST hub in the path, so the docking station and MST entries both apply. Worth checking, in this order:

  1. whether a /dev/i2c bus exists for the monitor at all while docked -- if not, see Nvidia and MST hubs
  2. whether ddcutil detect finds the monitor but DDC communication fails, which is the kernel-and-hub problem described under docking stations
  3. whether the same monitor and cable work in the machine's direct DisplayPort or HDMI output

Results vary between dock models with the same chipset, and between firmware revisions of one dock. A dock firmware update is worth trying before concluding anything.

Does ddcutil work with a GPU passed through to a virtual machine?

See Virtual Machines first: with a VM's built-in video driver there is no DDC/CI at all.

With a real GPU passed through, the guest sees a real card and ddcutil has been reported working there. On the host the card is bound to a stub driver such as vfio-pci, which creates no I2C adapters, so the monitor is not reachable from the host while the guest holds it.

The awkward case is switching: a monitor whose input is being switched between a host output and a guest output is being told to change input by whichever side currently has DDC access. Once the input moves away, that side can no longer reach the monitor to move it back. See switching inputs.

Raspberry Pi and other SoC systems

ddcutil works on several SoC boards, with two differences from a PC worth knowing.

The I2C controllers on these boards are platform devices, not PCI devices. ddcutil identifies video-related I2C buses partly by looking for a display controller class code on a PCI ancestor, which platform devices do not have, so bus identification relies on the adapter name instead. If ddcutil does not see a bus that you know carries a monitor, say so in a report and include ddcutil interrogate; the name based recognition is a list that gets extended.

DDC/CI timing is less forgiving on these boards. Failures that look like a broken monitor often turn out to be a too-short wait -- try --sleep-multiplier 2 before anything else.

On the Raspberry Pi specifically, see Raspberry Pi. Which bus carries HDMI DDC has changed across models and kernel versions; ddcutil detect with no options is the reliable way to find it, and a bus number from an older guide should not be assumed.

Running ddcutil detect wakes a sleeping monitor

Reported for some models. Reading the EDID and probing for DDC requires talking to the monitor, and some monitors treat any I2C activity as a reason to wake.

ddcutil avoids the probe where it can: when the DRM connector attributes for a bus are trustworthy, the EDID is read from /sys/class/drm rather than over I2C, and a display the DRM state reports asleep is not probed. Neither shortcut is available for every driver -- see the Nvidia sysfs entry -- and what remains is a genuine I2C read.

If a periodic detection is waking your monitor, the thing to look for is what is running detect on a timer. A desktop brightness applet polling through libddcutil is the usual answer.

Nvidia's proprietary driver

I'm using Nvidia's proprietary driver. ddcutil doesn't seem to be be working.

Symptoms include "DDC communication failed" on ddcutil detect, and lots of "Maximum retries exceeded" errors on command ddcutil getvcp known.

You may need the Nvidia secret handshake. See Special Nvidia Driver Settings.

I'm using Nvidia's proprietary driver. A monitor connected through an MST hub or docking station isn't detected at all.

The monitor works normally as a display. It simply does not appear in the output of ddcutil detect, and there is no I2C bus for ddcutil to try.

The Nvidia driver creates its I2C adapters when the kernel module is initialized, one per physical output on the card, and does not create one for a connector that appears later. A monitor attached through a DisplayPort MST hub does get a DRM connector of its own -- it appears under /sys/class/drm with a valid EDID, which the driver reads over the DisplayPort AUX channel -- but no I2C adapter is created to go with it. There is no /dev/i2c-* device for the connector, no ddc symlink in its directory, and no drm_dp_aux device. ddcutil communicates using /dev/i2c-*, so there is nothing for it to use.

To check whether this is what you are seeing, compare the number of Nvidia I2C adapters with the number of DRM connectors while the hub is attached:

$ ls /sys/bus/i2c/devices/i2c-*/name | xargs cat | grep -c NVIDIA
$ ls -d /sys/class/drm/card*-* | wc -l

Plug and unplug the hub and repeat. If the connector count changes while the adapter count does not, the monitors behind the hub have no I2C bus.

This is longstanding behavior, not a recent regression. It was reported on the Nvidia developer forum in November 2013 against driver 331.20, and acknowledged by an Nvidia developer as internally tracked bug 1417009. It has been observed unchanged on driver 580.173.02. Related ddcutil issues are #61 and #88.

There is nothing ddcutil can do about this. Making the monitor reachable requires the driver to expose a DDC channel for the connector.

Note that this is a different problem from the docking station failures described above, which were a limitation of the kernel drm layer and were fixed in kernel 5.11. It is also distinct from the case where an MST chain shares a single I2C bus and only the first monitor in the chain responds; there, at least one bus exists.

How much can the /sys/class/drm connector attributes be trusted with Nvidia's driver?

ddcutil reads edid, status and enabled from the connector directories under /sys/class/drm, as a faster and less intrusive alternative to probing each I2C bus. With Nvidia's driver there are reports of these attributes being wrong. They are the exception rather than the rule -- the attributes ordinarily do track a hotplug -- but they are worth knowing about, because when they occur the data ddcutil relies on is wrong before ddcutil ever sees it.

edid and status. There is a reported failure mode in which a connector directory is not populated after a hotplug. On driver 550.54.14 a user found edid empty with no usable DRM connector entry for a monitor that had just been plugged in; the report identifies libddcutil 2.1.5 as the software it broke. Note that this is a directory that was never filled in, not stale values left over from before the hotplug. Two workarounds were found: reboot, or as root

# echo detect > /sys/class/drm/card0-DP-2/status

which forces the entries to initialize. See Driver 550.54 - no update to /sys/class/drm/... on hotplug of monitor. Separately, issue 1084 reports that a force-enabled connector never sets link-status when the sink stops responding, so the DRM state can diverge from what is physically attached.

enabled. This one fails differently from the two above. Where edid and status are reported to go wrong after a hotplug, enabled can be wrong from the outset, because of a field the driver never sets. The kernel decides the value from connector->encoder; the Nvidia driver leaves that field unset and uses an internal one instead, so the attribute can report disabled for a monitor that is in use. Reported on Nvidia's forum around 2016, and again as issue 889 in 2025, and still open. systemd-logind, which uses enabled together with status to decide whether a laptop is docked, is affected by the same defect.

Switching between the proprietary driver and the open kernel modules is unlikely to change this. Issue 889 is filed against the open modules, but that says where it was reported, not where it occurs: the component that registers DRM connectors and populates these attributes is nvidia-drm, which is built from source at install time in both packages. What the open modules replaced is the core beneath it. Both also register the driver under the same name, nvidia, so nothing distinguishes them from ddcutil's point of view either -- the reliability determination is made from the driver name alone.

ddcutil does not rely on enabled.

dpms. Not used by ddcutil for detection, and not to be relied on generally. The kernel's own documentation states that userspace cannot rely on the DPMS value reflecting reality because many drivers fail to update it; it is a legacy property. That is a general warning, not an Nvidia-specific one -- no report of the sysfs dpms value being wrong under Nvidia in particular was found.

How much weight to put on the above: the hotplug reports are single-reporter, against one driver version, and were never acknowledged by Nvidia. They establish that the failure happens, not how often. The enabled defect is the better documented of the two, having been reported twice nine years apart with the cause identified.

The practical consequence is that if ddcutil detect disagrees with what is on your desk after a hotplug, and you are using the Nvidia driver, it is worth checking whether the connector directory under /sys/class/drm describes what is actually attached, before concluding the problem lies with the monitor or with ddcutil. If it does not, writing detect to the connector's status attribute, or rebooting, is worth trying.

What detect reports

The same DisplayPort connected monitor appears twice in the output of ddcutil detect.

Sometimes the same DisplayPort connected monitor is detected at 2 different I2C bus numbers. ddcutil detect reads the EDID at on both buses, but typically DDC communication succeeds on only 1 bus. ddcutil attempts to filter out the invalid bus, and refers to it as a "phantom" display. The invalid bus is a result of the implementation of the DisplayPort multistream facility. You can ignore the invalid entry. For more information, freedesktop.org i915 issue 3605 - Same MST display appears as 2 /dev/i2c devices contains an explanation of the complexity of MST topology

ddcutil detect --verbose reports that both I2C address x50 (EDID) and x37 (DDC) are responsive, but DDC communication fails.

There can be any number of reasons for this situation.

  • Check that DDC/CI communication is enabled in the monitor's on-screen display?
  • It has been observed in the case of a Tegra video card using the nouveau driver.
  • See also the discussions of duplicate entries for a DisplayPort monitor, and of failures with newer docking stations.

The detect command reports different EDIDs depending on how the monitor is connected to the video card.

Strange as it may seem at first, a monitor can have more than one EDID. The EDID for a VGA connection will have a different video input definition (byte x14) than that for a digital connection. The VGA version of the EDID will have timing information.

The detect command reports that I2C bus address x30 (EDID block number) is inactive.

EDID version 1.4 allows for addtional 128 byte EDID blocks. I2C bus address x30 specifies which block to read. These blocks generally contain extended timing information. ddcutil is interested only in the contents of the first EDID block. The check of bus address x30 is purely informational.

Capabilities, features and values

The capabilities command reports the MCCS (aka VCP) version, but elsewhere ddcutil says the version is unknown.

DDC/CI has two ways to get the the MCCS version:

  • As part of the capabilities string returned in response to a DDC Capabilities Request.
  • As the response to a VCP Feature Request for feature xDF (VCP Version).

Sometimes they disagree.

Command ddcutil capabilities reports the response to the DDC Capabilities Request. However, ddcutil regards this output as purely informational. (See capabilities command)

ddcutil therefore relies on VCP feature code xDF to determine the VCP version. (For USB connected monitors, it queries HID usage x00800004.) It is possible that feature code xDF is unsupported, even though the capabilities response specifies a version.

The output of the capabilities command is incorrect.

For example, a Dell P2210 monitor has VGA, DVI, and DisplayPort inputs, but capabilities only reports: 

 Feature: 60 (Input Source)
    Values (unparsed): 01 03
    Values (  parsed):
       01: VGA-1
       03: DVI-1

The capabilities string reported by a monitor is often incorrect. While the ddcutil capabilities command parses and reports the string, this is solely informational.

The only way to know for sure if a monitor supports a VCP Feature Code is by testing using the getvcp and setvcp commands.

The following command will attempt to read all VCP codes that ddcutil understands, other than those that are write-only: 

ddcutil getvcp known

To attempt to read all possible VCP codes, whether understood by ddcutil or not, except for those that are known to be write-only: 

ddcutil getvcp scan

To see all the values defined for a non-continuous (NC) feature code, i.e. one with discrete values, use the vcpinfo command with the --verbose option. For example, to see all the values defined in the Monitor Control Command Specification for VCP feature x60 (Input Source): 

# ddcutil vcpinfo 60 --verbose

VCP code 60: Input Source
   Selects active video source
   MCCS versions: 2.0, 2.1, 3.0, 2.2
   MCCS specification groups: Miscellaneous
   ddcutil feature subsets: 
   Attributes (v2.0): Read Write, Non-Continuous (simple)
   Attributes (v2.1): Read Write, Non-Continuous (simple)
   Attributes (v3.0): Read Write, Table (normal)
   Attributes (v2.2): Read Write, Non-Continuous (simple)
   Simple NC values:
      0x01: VGA-1
      0x02: VGA-2
      0x03: DVI-1
      0x04: DVI-2
      0x05: Composite video 1
      0x06: Composite video 2
      0x07: S-Video-1
      0x08: S-Video-2
      0x09: Tuner-1
      0x0a: Tuner-2
      0x0b: Tuner-3
      0x0c: Component video (YPrPb/YCrCb) 1
      0x0d: Component video (YPrPb/YCrCb) 2
      0x0e: Component video (YPrPb/YCrCb) 3
      0x0f: DisplayPort-1
      0x10: DisplayPort-2
      0x11: HDMI-1
      0x12: HDMI-2

In practice, any given monitor will implement only a few of the NC values, and some monitors will implement undocumented values. The only way to know for sure is by testing.

Two different monitors show the same capabilities output.

ddcutil caches capabilities strings so they need not be re-read from the monitor on every invocation. The cache is keyed by manufacturer, model name and product code, which is also the form used for user defined feature file names:

MFG-MODEL-PRODUCT_CODE

DEL-DELL_U3011-16485
SAM-LS34A650U-28996

That key identifies a monitor model only if the EDID actually fills in those fields. Some manufacturers ship a generic model name, such as "LG UltraWide", across an entire product line, and leave the product code unset -- 0, or sometimes 0x0101, which is what an EDID field filled with the byte x01 reads as. Two physically different monitors then produce the same key, and the capabilities string cached for the first is reported for the second.

ddcutil recognizes some of these. A small list of known generic model names, currently LG IPS FULLHD, LG UltraFine, LG Ultrawide, LG UltraWide and Samsung Syncmaster, combined with a product code of 0 or 0x0101, marks the identification as non-unique and the capabilities string is not cached. The test requires both conditions: a monitor whose name is not on that list is cached normally even when its product code is 0.

If two monitors report the same capabilities and you suspect this, check whether they share a key:

ddcutil detect | grep -E "Mfg id|Model|Product code"

If the product code is 0 and both monitors report the same model name, discard the cache and disable it for the affected runs:

ddcutil --discard-capabilities-cache detect
ddcutil --disable-capabilities-cache capabilities

Reading the capabilities string directly from the monitor each time is slower, but it is the value that monitor actually returned. Please report the manufacturer and model name so the generic name list can be extended.

Why do commands capabilities and vcpinfo report different information?

vcpinfo and capabilities get their feature value lists from different places.

vcpinfo reports the values given in the Mointor Control Command Set spec (MCCS). Its information is not monitor-specific. Option --mccs allows for selection of a specific MCCS version; if not given the most recent MCCS version in which the feature is defined, typically 2.2, is used.

capabilities reports the values shown on the capabilities string returned by the monitor. Normally, the interpretation of the value is that listed in the MCCS spec (reflecting the MCCS version of the monitor, as given in the capabilities string or, if that is not given, by querying feature xDF). If the value is unknown to the MCCS spec, "Unrecognized value" is reported. However, if the feature is defined in a user defined feature file for the monitor, the values reported for that feature are those in the UDF file, not those in the capabilities string, and the interpretation is that in the UDF file. (The uninterpreted string reported by capabilities is not modified by the UDF file; it is exactly that returned by the monitor.)

For example, many newer monitors have a USB-C input. No USB-C value for feature x60 (Input Source) is defined in any version of the MCCS spec, which is rather dated. Some manufacturers use x0b for its value, other manufacturers use a different value, and there's even no guarantee that a given manufacturer uses the same value on all its monitors. The only way for ddcutil to know about a USB-C value is for it to be defined it in a monitor-specific user defined features file.

As a further comment, the capabilities string can be unreliable. For example, the capabilities string reported by a Samsung U32H750 is "60( 11 12 0F)". The interpretation of those values, per the MCCS spec, is HDMI-1, HDMI-2, and DisplayPort-1. However those are not the actual values used by the monitor. The monitor recognizes x05 as HDMI-1 and x06 as HDMI-2. A user defined features file for the monitor, SAM_U32H75x-3586.mccs, could contain:

MFG_ID       SAM
MODEL        U32H75x
PRODUCT_CODE 3586
MCCS_VERSION 2.1
FEATURE_CODE 60 Input Source
  ATTRS NC RW
  VALUE x05 HDMI-1
  VALUE x06 HDMI-2
  VALUE x0f DisplayPort

setvcp 60 fails, or selects the wrong input

Feature x60 (Input Source) is the most frequently reported feature in ddcutil's issue history, and almost all of it comes down to one thing: the values are monitor specific, and the MCCS specification's list is both incomplete and widely ignored.

  • The spec defines no value for a USB-C input. Manufacturers picked their own; x0b and x1b have both been seen, and there is no guarantee a manufacturer is consistent across its own models.
  • Monitors use documented values to mean something else. A Samsung U32H750 answers to x05 and x06 for its two HDMI inputs, while its capabilities string advertises x11 and x12, which are the spec's HDMI values.
  • A value the monitor accepts may not appear in the capabilities string at all.

So the capabilities string is a starting point, not an answer. To find the real values:

ddcutil getvcp 60                 # what input is active now

Switch inputs using the monitor's own buttons, read x60 again after each, and record what you see. That gives you the monitor's actual value for each physical input, with no guessing. Write them into a user defined feature file so ddcutil reports them by name afterwards.

If setvcp 60 returns "Out of Range", the monitor rejected the value -- which is the good outcome, because it told you.

Switching input left me unable to switch back

Take this one seriously before experimenting with feature x60.

Setting the input to a source with nothing attached leaves the monitor showing no picture. If the monitor's OSD is also unavailable -- some models suppress it when there is no signal -- you cannot undo it from the monitor, and ddcutil cannot reach the monitor either, because the DDC channel belongs to the input that is no longer selected. There are reports of monitors left power cycling in this state after being sent an untested value.

Recovering, in increasing order of inconvenience: unplug the monitor's power for a minute, which resets some models; connect a signal to the input that is now selected and switch back with ddcutil from the machine driving it; or use the monitor's factory reset, if the OSD can be reached at all.

Precautions worth taking:

  • discover the valid values by reading x60 while switching with the monitor's buttons, as above, rather than by trying values to see what happens
  • have a second machine or cable on hand for the input you are switching to
  • do not sweep a range of values

Picture-in-Picture, KVM and other manufacturer extensions

Features for PiP and PbP layout, KVM switching, preset picture modes and OLED panel refresh are not in the MCCS specification. Manufacturers implement them as vendor-specific feature codes, and those are undocumented.

ddcutil can drive them once the codes are known, and it is often possible to find them:

ddcutil getvcp scan               # read every readable code, documented or not

Change the setting using the monitor's OSD, run the scan again, and compare. A code whose value tracked the change is a candidate. Record what you find in a user defined feature file, and please post it -- these are worth collecting, and other owners of the same model will find nothing else.

Treat writing to an unknown feature code with the caution described under switching inputs.

A feature's value looks wrong, or only the low byte changes

Continuous features carry a two byte value. Some monitors return only the low byte correctly, or report a maximum that does not match the range they actually accept. Where the two bytes matter, getvcp --verbose shows both, which is the way to tell a monitor returning a 16 bit value from one returning an 8 bit value in a 16 bit field.

Table valued features are a separate case: the MCCS spec defines feature x60 as a table feature in version 3.0 and a simple non-continuous feature in every other version, and monitors do not always agree with their own declared version.

setvcp does not change the feature value

Several Iilyama monitor models require that command scs (Save Current Settings) be issued immediately after a feature value is set. setvcp must be invoked with the --noverify option, followed immediately by scs.

Some monitors disable changing features such as brightness, contrast, and color when in Cinema or other special mode. Changing to a custom mode may enable these features.

The monitor supports Dynamic Contrast Range (DCR). setvcp for feature x10 (brightness) does not change the value

At least some monitors with Dynamic Contrast Range (DCR) disable feature x10 (brightness) and possibly other features when DCR is enabled. This has been reported with both Lenovo and Benq monitors.

The new value for feature x10 is different from the value specified on setvcp

It is common for the new value of a Continuous feature to be off by 1 from the specified value. This appears to be the result of integer to floating point to integer conversion in the monitor.

At least one monitor (Dell 2407wfp) does not allow setting brightness less than 30. setvcp values in the range 0..50 are mapped to to 30..50.

Performance

ddcutil is slow.

Typically, ddcutil spends 90% of its elapsed time in waits mandated by the DDC/CI protocol.

Two options can have a big impact on performance:

  • Option --bus. If the /dev/i2c bus number of the monitor is given, ddcutil skips the initial phase of searching the /dev/i2c devices for monitors. Note that if this option is specified, no other monitor selection option such as --display should be specified.

  • Option --sleep-multiplier. This option adjusts the length of time ddcutil spends in DDC/CI mandated waits. For example, if the DDC/CI protocol specifies a 40 ms wait between the time a command is sent to the monitor and the time a reply is read, and --sleep-multiplier .2 is given, ddcutil will only wait (.2 x 40 ms) = 8 ms. Some monitors have been found to communicate successfully with --sleep-multiplier values as low as .1. On the other hand, some monitors with poor DDC/CI implementations perform better if the sleep time is increased by using a value greater than 1.

What is dynamic sleep, and should I turn it off?

ddcutil must wait between DDC/CI operations. The required waits are specified, but the specified values are conservative, and most monitors work with less. Dynamic sleep observes how a monitor actually behaves and adjusts the multiplier as it goes, so a well behaved monitor gets faster over time without the user having to find a working --sleep-multiplier by hand.

It is not always an improvement. On a monitor whose failures are erratic rather than timing-related, the algorithm can chase noise, and one long-running report involved exactly that. The controls are:

ddcutil --disable-dynamic-sleep ...        # fixed multiplier
ddcutil --sleep-multiplier 1.5 ...         # or whatever value works

Both can go in the configuration file, which is the only way to apply them to libddcutil clients.

If you are diagnosing intermittent failures, disable dynamic sleep first so that the timing is one fewer variable.

My brightness script causes CPU spikes, or is slow to respond

Each ddcutil invocation pays for display detection before it can do anything. A script that runs ddcutil setvcp 10 repeatedly -- say from a hotkey that steps brightness -- pays that cost every time.

Reduce it:

  • pass --bus N or --display N so detection is skipped. --bus is the cheaper of the two. Get the number once from ddcutil detect.
  • pass --noverify if you do not need the value read back after setting it
  • avoid a loop of single-step invocations; compute the target value and set it once

For a program rather than a script, libddcutil detects displays once and keeps them, which avoids the problem entirely.

libddcutil, KDE Plasma and PowerDevil

KDE Plasma 6

ddcutil commands fail after upgrade to version 2.0 and KDE Plasma 6

ddcutil 2.0 added a cross-instance locking facility. The problem addressed was random failures when multiple ddcutil or libddcutil instances clobber each other's DDC transactions. Internally, ddcutil uses what are called display handles to represent /dev/i2c devices that have been opened at the OS level. Proper use of the API is, for each DDC transaction, to open a display, creating a display handle, perform the transaction, and then close it. This sounds expensive, but in fact the time spent opening and closing is negligible compared to the time spent performing the I2C operations of a DDC transaction.

When the cross-instance locking facility is enabled, and a display is opened creating display handle, ddcutil calls flock() on the underlying /dev/i2c device and holds the flock until the handle is closed. Unfortunately, at startup PowerDevil creates a display handle for each /dev/i2c device and never closes it. So the flock's are never released, blocking other ddcutil instances.

Cross-instance locking can be disabled using option --disable-cross-instance-locks. This option can be specified on the ddcutil command line, or in configuration file $HOME/.config/ddcutil/ddcutilrc. The latter is the only way to control libddcutil, which is used by PowerDevil. For a description of configuration files, see https://www.ddcutil.com/config_file.

Powerdevil crashes repeatedly with ddcutil 2.1.0

ddcutil 2.1.0 API introduced an initialization function, ddca2_init(), into the libddcutil API to give the client, e.g. PowerDevil, finer control of libddcutil's initialization. If the initialization function is not called, then default settings are used. There was a bug in default initialization that caused PowerDevil to crash repeatedly. This was fixed in ddcutil 2.1.2. Also, PowerDevil was changed to explicitly call the initialization function, thereby avoiding the bug. With two different fixes for same problem, it may not be obvious what change made PowerDevil work again.

PowerDevil crashes or hangs at login, and takes the desktop's power management with it

PowerDevil calls libddcutil during startup, unconditionally -- the "Control hardware brightness with DDC/CI" setting in Plasma's display settings governs whether an already detected DDC/CI display gets used, not whether PowerDevil scans for one. So a libddcutil failure at initialization becomes a PowerDevil failure, and systemd gives up after a few restarts, leaving plasma-powerdevil.service failed and the session without brightness policy, idle timeouts or suspend-on-lid.

To take libddcutil out of the path while diagnosing, PowerDevil honors an environment variable:

systemctl --user edit plasma-powerdevil.service
# [Service]
# Environment=POWERDEVIL_NO_DDCUTIL=1
systemctl --user reset-failed plasma-powerdevil.service

That disables DDC/CI brightness control for all external monitors in the session; the internal laptop backlight and KWin's own brightness control are unaffected. It is a diagnostic and a stopgap, not a fix -- if you need it, the underlying libddcutil problem is worth reporting, with the coredumpctl output described above.

The desktop lags for several seconds after resume from sleep

Display detection has to happen again after resume, and it costs real time: every candidate I2C bus is opened and probed. When a desktop component does that synchronously on the resume path, the delay is visible.

Two things make it worse than it needs to be, both of them addressed in recent releases and worth checking your version against:

  • the EACCES window described above, where the devices are not yet accessible and the work is wasted
  • buses that no DRM connector claims being probed at all. On some drivers a read into silence spends hundreds of milliseconds inside the driver before failing, and the bus lock is held for the duration, so other ddcutil instances wait too

If a resume is slow on a current release, a report with --syslog debug --trace-to-syslog spanning the resume is what shows where the time went.

libddcutil does not seem to read my configuration file

libddcutil reads the same $HOME/.config/ddcutil/ddcutilrc as the command line program, but which section applies is not the same. Options in the [ddcutil] section apply to the command line program. A libddcutil client picks up the [libddcutil] section, and a client may also pass its own options, which take precedence. See Configuration File.

Two further reasons a setting may appear to be ignored:

  • the client called ddca_init2() with its own options, which is the supported way for a client to configure the library and overrides the file
  • the process is not running as you. A system service reads the configuration of the user it runs as, which for a system-wide daemon is not your home directory

To confirm what the library actually resolved, a client can call ddca_report_build_options() and the settings reporting functions; the command line equivalent is ddcutil --settings.

libddcutil behaves differently from the ddcutil command after a monitor is plugged in

The command line program detects displays once per invocation and exits, so it always sees current hardware. A libddcutil client is long lived and holds the display list it built at initialization.

If the client has enabled display watching, libddcutil updates the list as monitors come and go and reports the change through a callback. If it has not, the list is whatever was there at initialization until the client calls ddca_redetect_displays(). A client that neither watches nor redetects will not see a newly connected monitor at all, and will learn that a removed one is gone only when an operation on it fails.

Specific hardware and environments

ddcutil hangs on Radeon RX 5xxx and 6xxx cards (Navi and Navi2 GPU)

There have been multiple reports of ddcutil command failures on Radeon cards with the Navi and Navi2 GPUs (RX 5xxx and RX 6xxx cards).

In some cases ddcutil hangs. (See for example issues Stop poking AMDGPU SMU I2C #194, Screen freeze when changing brightness #223).. The SMU related hang should have been fixed as of kernel 5.14.4. ddcutil has had a workaround since release 1.1.0.

In other cases, the monitor's EDID is simply not detected.

If your kernel version is 5.14.4 or later, I suggest you file a bug report at the amd driver issue list.

Include: - drm output - the kernel log file (/var/log/kernel on Ubuntu) - output of the following commands

$ sudo ps -aux | grep ddcutil
$ sudo awk ' {print FILENAME ": " $0 } '  /sys/bus/i2c/devices/*/name

Does ddcutil work in containers?

User Nikolay Dandanov has reported success running ddcutil in a Docker container:

I defined a new Arch Linux image for Docker using the following simple Dockerfile:

FROM archlinux:latest

RUN pacman --noconfirm -Syu && \
    pacman --noconfirm -S ddcutil && \
    rm -rf ~/.cache/*

I saved this to a file named Dockerfile and built a Docker image using ~~~docker build -t ddcutil:v0.0.1~~~.

I then ran the container and also mapped all i2c devices (otherwise, these were not available in the container):

docker run $(for dev in `ls /dev/i2c*`; do echo "--device $dev "; done) -it --name ddcutil ddcutil:v0.0.1

See also this stackoverflow post: How to fix ddcutil for a docker container

Building ddcutil

configure complains that a required package does not exist, but it is installed on my system.

When building ddcutil, error messages from pkg-config (which is called by configure) can be misleading. If configure complains that a package is not found but it seems to be installed, it's likely that what's missing is the associated development package (with a suffix like "-dev").

Building on NixOS, or building statically

Both are reported working, with the usual caveats.

ddcutil discovers its dependencies with pkg-config, so on NixOS the development inputs must be in the build environment rather than merely installed -- the missing package entry above applies, and a nix-shell with the -dev outputs of glib, libusb, libdrm, jansson, libudev and the X libraries is the usual arrangement.

For a static build, disable the optional subsystems you do not need so their libraries do not have to be resolved statically:

./configure --disable-usb --disable-x11 --disable-dbus

--disable-udev is possible too, at the cost of falling back to a less reliable method of enumerating I2C devices.

Installing into a staging directory

make DESTDIR=/path/to/stage install

is supported and is what packagers use. If a file lands outside the staging tree, that is a bug worth reporting -- it has happened, and been fixed, more than once. The CMake support file FindDDCUtil.cmake has also been installed to the wrong location in the past; check it if a CMake based consumer cannot find ddcutil.
